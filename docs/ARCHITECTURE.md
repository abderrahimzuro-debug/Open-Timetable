# التصميم المقترح — Open-Timetable

> حالة المستند: **مقترح** بانتظار قرارك حول نوع الواجهة (راجع `docs/BLOCKERS.md`، العائق B5).

## الفكرة في سطر واحد

واجهة عربية حديثة (RTL) تُستخدم من المتصفح لإدخال بيانات المدرسة والقيود، وتُولّد الجداول
باستخدام محرّك FET نفسه (المعروف بجودة نتائجه) عبر تشغيله كعملية منفصلة.

## لماذا لا نعدّل واجهة Qt؟

| | تعديل Qt في مكانه | واجهة ويب جديدة |
| --- | --- | --- |
| تكلفة التطوير | 337 ملفًا/7.9MB، بنية قديمة مترابطة | بناء من الصفر ببنية حديثة |
| المعاينة والاختبار | يحتاج بناء Qt على كل جهاز | تعمل في المتصفح مباشرة |
| العربية وRTL | محدودة في تخطيطات Qt Widgets | دعم كامل وسهل |
| العمل الجماعي والصلاحيات | غير متوفر | متوفر بطبيعته (خادم + حسابات) |
| إعادة الاستخدام | سطح مكتب فقط | أي جهاز، ويمكن الطباعة والمشاركة برابط |
| المخاطر | كسر المحرّك أثناء التعديل | صفر — المحرّك يبقى كما هو |

القاعدة التي نلتزم بها: **لا نلمس كود المحرّك**. نتعامل معه عبر صيغة `.fet` (مدخلات) ومخرجاته
(`timetables/`)، وهذا يعطينا كامل حرية الواجهة دون مخاطرة على صحة التوليد.

## المعمارية

```
┌────────────────────────────── المتصفح ──────────────────────────────┐
│  واجهة عربية RTL (Next.js/React + TypeScript)                        │
│  • معالج إعداد (Wizard): سنوات/مجموعات ← مواد ← أساتذة ← قاعات ← حصص   │
│  • محرّر قيود مبسّط (قوالب جاهزة + خيارات متقدمة)                     │
│  • لوحة تشغيل: تقدّم التوليد، إلغاء، سجلات                            │
│  • عارض جداول: لكل صف/أستاذ/قاعة، طباعة/PDF، تصدير CSV/HTML           │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ HTTP (روابط نسبية /api)
┌───────────────────────────────▼──────────────────────────────────────┐
│  الخادم (Node.js/TypeScript)                                         │
│  • REST API + التحقق من الصحة (Zod)                                  │
│  • قاعدة بيانات (SQLite محليًا / PostgreSQL للإنتاج)                   │
│  • مولّد `.fet` (XML)  ←→  قارئ `.fet` (استيراد ملفات موجودة)          │
│  • مدير المهام (Job Queue): تشغيل في الخلفية + حد زمني + إلغاء         │
│  • محوّل المخرجات: HTML/XML من `timetables/` → JSON للواجهة            │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ subprocess (stdin/args, لا shell)
┌───────────────────────────────▼──────────────────────────────────────┐
│  مشغّل المحرّك (Engine Runner)                                        │
│  واجهة واحدة مع تنفيذين:                                             │
│   • real  → fet-cl --inputfile=... --outputdir=... --timelimitseconds│
│   • mock  → يولّد جداول وهمية واقعية (للتطوير والمعاينة بلا Qt)        │
└──────────────────────────────────────────────────────────────────────┘
```

## قرارات معمارية (ADRs)

### ADR-001: المحرّك كعملية منفصلة
- **القرار:** تشغيل `fet-cl` كـ subprocess، لا عبر ربط C++ مباشر.
- **السبب:** عزل الأعطال (تعطّل المحرّك لا يُسقط الخادم)، إمكانية قتل العملية عند تجاوز الوقت،
  وعدم الارتباط بإصدار Qt، والحفاظ على مصدر FET غير معدّل (متوافق مع AGPL).
- **البديل المرفوض:** تضمين كود C++ في خدمة Node عبر addon — تعقيد بناء كبير بلا مقابل.

### ADR-002: التطوير بمحرّك وهمي (mock) عند غياب المحرّك
- **القرار:** واجهة `EngineRunner` مع تنفيذ `mock` يعمل دائمًا، و`real` عند توفر `fet-cl`.
- **السبب:** بيئة العمل لا تحتوي Qt (العائق B1)؛ وهذا لا يجب أن يمنع بناء الواجهة ومعاينتها.
- **الأثر:** كل اختبارات الواجهة تعمل بلا محرّك، مع اختبار تكامل منفصل للمحرّك عبر CI.

### ADR-003: صيغة التبادل هي `.fet` (XML)
- **القرار:** كل تفاعل مع المحرّك يمر عبر ملف `.fet` والملفات الناتجة في `timetables/`.
- **السبب:** موثّقة عمليًا، ولدينا 327 ملفًا حقيقيًا للاختبار، وتتيح الاستيراد من نسخ FET الموجودة
  عند المستخدمين (مهم جدًا للمدارس التي لديها ملفات جاهزة).
- **تفصيل:** يجب التعامل مع BOM، وإصدارات `<fet version="...">` المختلفة، وترميز UTF-8 على ويندوز.

### ADR-004: حدّ زمني إلزامي + مهام خلفية
- **القرار:** لا طلب HTTP ينتظر المحرّك؛ كل توليد = مهمة (job) لها حالة وحد زمني وإلغاء.
- **السبب:** التوليد قد يستغرق من ثوانٍ إلى ساعات (العائق B10).

### ADR-005: الرخصة AGPL-3.0 للمشروع كله
- **القرار:** الكود الجديد يُنشر تحت AGPL-3.0 (لتوافق الاستدعاء/التوزيع مع FET).
- **الأثر:** يجب إتاحة الكود لمن يستخدم الخدمة عبر الشبكة (راجع `NOTICE.md`).

## نموذج البيانات (الحد الأدنى)

الكيانات مطابقة لما يفهمه FET، حتى يكون التحويل سلسًا:

- `Institution` — اسم المؤسسة، ملاحظات
- `Year` / `Group` / `Subgroup` — هيكل الطلاب (مع `number_of_students`)
- `Subject`, `Teacher`, `ActivityTag`, `Building`, `Room`
- `Day`, `Hour` — الأيام والحصص (مع دعم الفترات الصباحية/المسائية)
- `Activity` — مادة + أستاذ + مجموعة/فوج + مدة (عدد الحصص) + وسوم
- `Constraint` — قيود زمنية ومكانية (نبدأ بمجموعة صغيرة شائعة ثم نوسّع تدريجيًا)
