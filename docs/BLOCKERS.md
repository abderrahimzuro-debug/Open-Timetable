# تقرير العوائق (Blockers) وخطة إزالتها

> تاريخ الفحص: 2026-10-29 — بيئة: Debian 12 (bookworm)، Python 3.11، Node 22، مساحة 19GB، ذاكرة 3.8GB.
> الغرض: حصر كل ما يعيق العمل على الواجهة الجديدة **قبل** البدء بها، وإزالة ما يمكن إزالته فورًا.

## تفصيل كل عائق مع الدليل

### B1 — لا Qt ولا CMake في بيئة العمل، ولا وصول لمستودعات Debian

**الدليل (مُختبر فعليًا):**

```text
$ which cmake qmake qmake6            → (لا شيء)
$ sudo apt-get update                 → W: Failed to fetch http://deb.debian.org/... Connection failed
$ curl -sI http://deb.debian.org/     → code=000  (محجوب)
```

فحصت أيضًا إمكانية جلب Qt من PyPI: حزمة `PySide6-Essentials` نُزّلت بنجاح، لكنها **لا تحتوي
ملفات رأس (headers) ولا Qt6Config.cmake**:

```text
include/QtCore/*.h : 0
lib/cmake/Qt6      : 0
```

⇒ لا يمكن بناء كود C++ ضدها. لذلك **البناء يحدث خارج بيئة العمل** بأحد هذه الطرق:

1. **Docker:** `docker build -f docker/engine.Dockerfile -t open-timetable-engine .`
2. **CI على GitHub Actions:** `.github/workflows/engine.yml` (يبني، يختبر، ويرفع `fet-cl` كأثر قابل للتنزيل).
3. **جهازك:** `sudo apt install build-essential qtbase5-dev` ثم `./scripts/fet-build-cl.sh`.

**قرار تصميمي مستفاد:** الواجهة الجديدة يجب ألّا تعتمد على تصريف المحرّك مباشرة داخل عملية الخادم،
بل عبر **مشغّل محرّك (Engine Runner)** بواجهة ثابتة، مع **محرّك وهمي (mock)** للتطوير ومعاينة
الواجهة دون الحاجة إلى Qt. هذا يتيح بناء الواجهة كاملة الآن، وتبديل المحرّك الحقيقي لاحقًا بسطر إعداد.

### B2 — ملفات GitHub Releases محجوبة

```text
$ curl -L .../releases/download/v7.10.5/fet-cl-7.10.5-linux-x86_64.tar.gz
  → 302 إلى release-assets.githubusercontent.com
$ curl -sI https://release-assets.githubusercontent.com/   → code=000 (محجوب)
```

حُلّ بالبديل: نبنيه بأنفسنا من المصدر الموثّق (B1)، وهو الأفضل أمنيًا على أي حال.

### B3 — تعارض إصدار Qt

| المسار | الشرط الرسمي | التوفّر على التوزيعات |
| --- | --- | --- |
| CMake (`CMakeLists.txt`) | `find_package(Qt6 6.10 REQUIRED)` | نادر (Ubuntu 24.04 = Qt 6.4) |
| QMake (`src/src-cl.pro`) | Qt ≥ **5.15** (مذكور صراحة في الملف) | متوفّر دائمًا (Ubuntu 22.04 = 5.15.3) |

لا يوجد في المصدر أي استخدام لواجهات Qt6 الحصرية (فحص `QStringView`/`QAnyStringView` = 0 تطابق).
⇒ اعتمدنا `qmake` + Qt 5.15 في السكربتات وDocker وCI؛ ويبقى مسار CMake متاحًا لمن لديه Qt 6.10+.
هذا القرار **قابل للتغيير** لاحقًا دون أثر على الواجهة.

### B4 — الحجم

```text
fet-7.12.0.tar.xz   = 8.9 MB  (المحفوظ في Git)
بعد الفك            = 352 MB / 897 ملفًا
├── translations/   = 190 MB
├── examples/       = 142 MB
├── src/            =  18 MB (396 ملفًا)
└── doc/, icons/    = 2.2 MB
```

لذلك: لا تُحفظ الشجرة المفكوكة أبدًا. `scripts/fet-extract.sh` يفكّها في `.fet-src/` وهو مستثنى
في `.gitignore`. وإن احتجنا لاحقًا لتعديل كود C++ فسنُدخل **مجلد `src/` فقط** (18MB) أو نطبّق
تعديلاتنا كـ patch فوق الأرشيف.

### B5 — الواجهة الحالية (العائق الأساسي لهدفك)

| المقياس | القيمة |
| --- | --- |
| ملفات الواجهة | 337 ملفًا / 7.9MB |
| التقنية | Qt Widgets (C++17)، تصميم من التسعينيات/بدايات الألفية |
| المشكلة | نماذج متشعّبة، عشرات الحوارات، لا دعم RTL جيد للعربية في التخطيطات، لا معاينة خارجية |
| القيود العملية هنا | لا يمكن تصريفها ولا معاينتها في هذه البيئة (B1) |

**الخيارات (تحتاج قرارك):**

1. **واجهة ويب جديدة (موصى به):** واجهة عربية حديثة RTL تعمل في المتصفح، والحساب/التوليد عبر خادم
   يشغّل `fet-cl`. الميزة: تفتحها من أي جهاز، سهلة التطوير والمعاينة، تصدير/طباعة أفضل.
   العيب: تحتاج خادمًا (أو Docker) لتشغيل المحرّك.
2. **تحديث واجهة Qt في مكانها:** الحفاظ على برنامج سطح مكتب، لكن التكلفة عالية، والتحقق يحتاج
   بناء Qt على جهازك في كل مرة.
3. **هجين:** واجهة ويب للاستخدام اليومي + بقاء نسخة Qt لمن يريد العمل دون خادم (دون تعديلها الآن).

### B6 — الرخصة

FET تحت **AGPL-3.0**. إن قدّمنا خدمة توليد جداول عبر الشبكة، تصبح الخدمة (وبالتالي كود
Open-Timetable) مطالَبة بأن تكون مفتوحة تحت الرخصة نفسها. أُضيف `LICENSE` (نص AGPL-3.0 الكامل
من الأرشيف الرسمي) و`NOTICE.md` يوضّح المصدر والالتزامات. الالتزام بالمفتوح هنا **ليس عائقًا**
بل هو المشروع نفسه — المهم ألّا نبني لاحقًا على أساس يخالف الرخصة.

### B7 — لا اختبارات

أُضيف:
- `scripts/fet-verify.sh` — التحقق من بصمة SHA-256 للأرشيف (+ محاولة تحقق GPG).
- `scripts/fet-extract.sh` — فكّ موثّق.
- `scripts/fet-build-cl.sh` — بناء آلي بأي من الطريقتين.
- `scripts/fet-smoke-test.sh` — توليد جداول من 3 ملفات حقيقية والتحقق من المخرجات.
- `.github/workflows/engine.yml` — تشغيل كل ما سبق على كل تعديل يمسّ المحرّك.

### B8 — صيغة `.fet`

- الملفات تبدأ بـ **BOM** (`\uFEFF`) قبل `<?xml ...>` ⇒ أي قارئ يجب أن يتعامل معها.
- سمة الإصدار في الجذر (`<fet version="5.41.0">`) تختلف بين الملفات القديمة والجديدة.
- 327 ملف `.fet` حقيقي متوفر داخل الأرشيف لاختبار أي قارئ/كاتب نكتبه (بدون Qt).

### B9 — بيئة المعاينة

المعاينة تعمل على نطاق خارجي: يجب أن يكون الخادم مربوطًا على `0.0.0.0`، والواجهة تستخدم روابط
**نسبية**، وأي مسار `/api` يُوجَّه عبر نفس الخادم (proxy) لا عبر `localhost`.

### B10 — الأداء

المحرّك قد يستغرق دقائق (وأحيانًا ساعات) في الحالات الصعبة. لذلك في التصميم: حدّ زمني إلزامي،
تشغيل في الخلفية مع متابعة الحالة، وإمكانية الإلغاء — لا انتظار داخل طلب HTTP.

scripts/fet-extract.sh         فكّ المصدر إلى .fet-src/
scripts/fet-build-cl.sh        بناء fet-cl (qmake أو cmake)

.github/workflows/engine.yml   بناء + اختبار آلي

## ما ينتظر قرارك (وليس تنفيذي)

1. **نوع الواجهة:** ويب (موصى به) / Qt في مكانه / هجين.
2. **من يستخدم النظام:** مدير جداول فقط، أم مدير + أساتذة + طلاب؟
3. **التشغيل:** استضافة سحابية، أم على جهاز في المدرسة (سطح مكتب)، أم كليهما؟
4. **البيانات:** هل لديك ملفات `.fet` جاهزة من مدرستك/جامعتك نبدأ بها؟

بمجرد اختيارك (1)، تكون كل العوائق التقنية أمام التنفيذ قد أُزيلت.
